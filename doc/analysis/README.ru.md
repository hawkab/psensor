# Анализ нагрузки и нагрева в Psensor

Пункт трея **«Анализ нагрузки и нагрева»** открывает небольшое окно с главным
выводом: что сейчас или недавно могло нагреть процессор. Крупно показаны
температура и общая загрузка; ниже — текущая работа, недавняя работа и режим
питания. Диапазон температур за последние 15 минут и пик чиплета помогают
увидеть короткие всплески. Журнал ядра проверяется за два часа при открытом окне.

**«Подробнее»** открывает отдельное окно с графиками и таблицами текущей и
недавней нагрузки. Ссылки на процессы открывают инспектор: роль процесса,
PID, пользователь, родитель, исполняемый файл, рабочая папка, память и потоки.
Для распознанных задач показаны эмулятор Android, сборка Gradle и контейнер.
Инспектор читает доступные сведения ОС, а не содержимое выполняемых инструкций.
Завершённый процесс сохраняет вклад в недавнюю нагрузку.

Вывод о нагреве — оценка по активности CPU и времени, включая 30 секунд перед
температурным пиком. Температура отдельного процесса не измеряется. Задачи
короче двух секунд могут быть пропущены, недоступные сведения отмечаются в UI.
100% CPU процесса означает один логический поток; общая загрузка учитывает все
потоки. Низкая общая загрузка может сочетаться с нагревом отдельных ядер.

## Команда по датчику

В свойствах **каждого датчика** появилась вкладка **«Действие»**:

1. Выберите условие: значение не меньше или не больше порога.
2. Задайте порог, непрерывную длительность и гистерезис повторного взведения.
3. Введите команду, включите правило и нажмите **«Сохранить правило»**.

Все правила изначально выключены. Предустановка сбалансированного режима
только заполняет `powerprofilesctl set balanced`; включение требует сохранения.
Смена режима может снизить частоту, потребление и нагрев, но задачи могут
выполняться дольше. Она не прекращает работу процесса и не гарантирует меньший
процент загрузки. Доступность режимов зависит от ОС и оборудования.

Команда запускается асинхронно через `/bin/sh -c` с правами пользователя,
один раз на непрерывный выход за порог. Следующее срабатывание возможно после
возврата за порог с гистерезисом. Пропуски и устаревшие измерения прерывают
отсчёт; нулевые обороты вентилятора являются допустимым измерением.
Изменение правила не меняет уже запущенную команду.

Команде доступны переменные `PSENSOR_SENSOR_ID`, `PSENSOR_SENSOR_NAME`,
`PSENSOR_VALUE`, `PSENSOR_THRESHOLD`. Температурные значения передаются в °C,
даже при показе °F. Например, можно записать событие:

```sh
printf '%s: %s\n' "$PSENSOR_SENSOR_NAME" "$PSENSOR_VALUE" >> "$HOME/psensor-events.log"
```

После завершения команды Psensor показывает стандартное системное уведомление:
датчик и условие, фактическая команда, результат и локальное время в формате
`чч:мм:сс дд.мм.гггг`. Ошибка запуска и ненулевой код завершения также видны.
Нажатие уведомления открывает вкладку «Действие» нужного датчика через
`psensor://sensor/<идентификатор>?tab=action`. Это требует регистрации desktop-записи;
показ уведомлений и действие клика поддерживаются оболочкой рабочего стола.

## Сборка и установка для текущего пользователя

Нужны Linux, GTK 3.22+, GLib/GIO 2.66+, Ayatana AppIndicator, libsensors,
libgtop, libnotify, autotools и компилятор C. Для анализа нужны Python 3.9+,
PyGObject, GTK3, Cairo, dbus-python и sqlite3. GNOME требуется расширение,
поддерживающее AppIndicator. Установка служб рассчитана на systemd user session.

Пример зависимостей для Debian/Ubuntu (названия пакетов зависят от дистрибутива):

```sh
sudo apt install build-essential autoconf automake gettext autopoint pkg-config \
  libgtk-3-dev libayatana-appindicator3-dev libsensors-dev libgtop2-dev \
  libnotify-dev python3-gi python3-gi-cairo python3-dbus \
  desktop-file-utils xdg-utils help2man
```

В корне репозитория:

```sh
autoreconf -fi
./configure --prefix="${XDG_DATA_HOME:-$HOME/.local/share}/psensor-analysis/runtime"
make -j2
# При повторной установке остановите службы перед заменой файлов.
systemctl --user stop psensor-ui.service psensor-analysis.service
make install
python3 scripts/install-user.py --start
```

Если службы ещё не установлены, сообщение `Unit not loaded` при остановке можно
пропустить. Перед первым запуском завершите ранее запущенный экземпляр Psensor:
приложение использует единое имя D-Bus. Системный пакет не перезаписывается.
`make install` устанавливает все семь Python-модулей и PNG значки.

При другом `--prefix` передайте такой же путь в
`scripts/install-user.py --runtime-prefix /путь/к/prefix --start`.
Скрипт создаёт две пользовательские службы, desktop-запись с `%U` и MIME-схемой,
автозапуск, регистрирует схему и включает службы. Перед заменой отличающихся
конфигураций сохраняется копия `.previous-ДАТА-ВРЕМЯ`.
`--no-register` создаёт только файлы, без обращения к systemd или рабочему столу.

Обычно модули читаются из `PREFIX/share/psensor-analysis`. Также поддерживаются
старое расположение `XDG_DATA_HOME/psensor-analysis` и явный `PSENSOR_ANALYSIS_DIR`.
Для обычной системной сборки можно использовать стандартный `make install`,
но службу истории и регистрацию URI необходимо настроить для пользователя.
Без сборщика окно не располагает историей до своего открытия.

Обороты вентиляторов приходят через libsensors/hwmon, когда соответствующий
драйвер предоставляет `fan*_input`. См. [инструкцию IT8689](FANS.md).

## Проверки

После `configure` и сборки:

```sh
sudo apt install xvfb dbus-x11
python3 tests/analysis/run.py
```

Тесты используют временные БД и приватные D-Bus/Xvfb-сеансы. Они не меняют
правила или службы работающего Psensor. Проверяются объяснение нагрузки,
накопительный расчёт истории, пакетная запись и публикация буфера, настройки
команд, асинхронное выполнение, уведомления и открытие URI, ленивые модули,
закрытие соединения/потока, отсутствие утечки подписи трея и лишней отрисовки.
`--no-gui` пропускает интеграционные проверки графики и уведомлений.

## Работа в фоне и отзывчивость

Сборщик сохраняет компактную историю каждые две секунды, до 24 часов.
Без окон запись объединяется за десять секунд; открытие трея публикует
последний буфер без дополнительного опроса. Анализ, проверка журнала, графики
и инспектор создаются по запросу. После закрытия всех окон процесс UI завершается.
Подробнее об алгоритмах и измерениях — [PERFORMANCE.md](PERFORMANCE.md).

GTK больше не ждёт mutex занятого поставщика датчиков: обновление, отрисовка,
применение настроек и очистка используют trylock и пропускают занятый проход.
Старый глобальный сценарий уведомления также запускается асинхронно.
Это устраняет блокировку интерфейса из-за ожидания поставщика или команды;
сам зависший драйвер/внешний поставщик этим не исправляется.
В настройках запуска выбран X11 backend для совместимости трея через XWayland.

## Отключение и восстановление

```sh
systemctl --user disable --now psensor-ui.service psensor-analysis.service
```

Удалите или восстановите из `.previous-*` созданные файлы:
`XDG_CONFIG_HOME/systemd/user/psensor-{ui,analysis}.service`,
`XDG_CONFIG_HOME/autostart/psensor.desktop`,
`XDG_DATA_HOME/applications/psensor.desktop`, затем выполните
`systemctl --user daemon-reload` и `update-desktop-database` для каталога applications.
Если имеется системный пакет, его desktop-запись снова станет доступна.
Локальный runtime можно удалить отдельно; правила Psensor и история в
`XDG_STATE_HOME/psensor-analysis` остаются до явного удаления.
